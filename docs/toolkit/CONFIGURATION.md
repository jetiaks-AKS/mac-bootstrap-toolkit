# Конфигурация Mac Bootstrap Toolkit

## Назначение

Конфигурационная система Toolkit отделяет данные рабочего окружения
от логики его обработки.

Она связывает основные этапы системы:

```text
Current Mac
    ↓
Discovery
    ↓
Generated Configuration
    ↓
Blueprint
    ↓
Bootstrap
```

Dry-run и отдельный Verification пока не реализованы.

---

# Два состояния конфигурации

Toolkit разделяет фактическое и целевое состояние.

### Observed State

Состояние, обнаруженное на текущем Mac.

Оно формируется Discovery и сохраняется в:

```text
config/generated/
```

### Desired State

Состояние, которое должно быть получено на целевом Mac.

Оно определяется Blueprint.

```text
Observed State
      ↓
   Blueprint
      ↓
Desired State
```

Такое разделение позволяет сохранить существующее окружение
как основу, но независимо определить, что именно необходимо
восстановить.

Generated Configuration используется Bootstrap как источник фактических
значений. При наличии локального Blueprint он определяет выбранную часть этого
состояния; без Blueprint Bootstrap сохраняет полный scope.

---

# Generated Configuration

`config/generated/` — основной результат работы Discovery.

Здесь хранится автоматически сформированное описание
обнаруженного рабочего окружения.

Каталог может содержать конфигурации для:

* приложений;
* Git;
* Workspace;
* VS Code;
* macOS Settings;
* других компонентов Toolkit.

Структура каталога может расширяться вместе с развитием проекта.

Generated Configuration не должна требовать ручного дублирования
пользовательских настроек в Bootstrap-коде.

Generated Configuration является machine-specific результатом
Discovery и не является частью публичного Git-состояния проекта.

Каталог `config/generated/` исключён из Git через `.gitignore`.

При этом файлы остаются доступными локально и используются
Bootstrap после выполнения Discovery.

---

# Статическая конфигурация Toolkit

Каталог `config/` используется для настроек самого Toolkit
и других данных, которые не являются результатом Discovery.

Таким образом:

```text
config/
    → конфигурация самого Toolkit

config/generated/
    → обнаруженное состояние рабочего окружения
```

Эти два типа конфигурации не должны смешиваться.

Статическая конфигурация проекта может храниться в Git,
если она не содержит machine-specific или пользовательских
данных.

---

# Blueprint

Generated Configuration описывает:

> **что есть сейчас.**

Blueprint определяет:

> **что должно быть.**

Blueprint сейчас предоставляет parser, validation, item-level и
category/module-level фильтрацию Bootstrap. Пользовательский
`config/blueprint.conf` содержит только выбор категорий и отдельных
обнаруженных компонентов; реальные значения остаются исключительно в
`config/generated/`.

Blueprint MVP реализован и прошёл полную E2E-проверку в ветке `develop`; в
стабильный релиз 2.0.1 эта функциональность ещё не входит.

Файл Blueprint локальный, исключён из Git и не создаётся автоматически.
Нейтральная структура формата приведена в
`config/blueprint.example.conf`.

При наличии Blueprint Bootstrap фильтрует Homebrew packages и casks,
приложения App Store, расширения VS Code, папки Workspace и Git-репозитории по
item-секциям. Без Blueprint сохраняется прежняя обработка всех компонентов из
Generated Configuration.

Для `[workspace-folders]` обычными Blueprint-кандидатами являются только записи
`folders.conf` с классификацией `workspace`. Наблюдаемые каталоги `user` и
`system` остаются в Generated Configuration, но не входят в обычный выбор
Blueprint. При отсутствии Blueprint сохраняется broad legacy-обработка всех
наблюдаемых записей.

Секция `[categories]` независимо управляет Git Configuration, VS Code Settings
и модулями macOS Finder, Dock, Keyboard, Trackpad и Screenshots. Interactive CLI
доступен через последовательный workflow:

```text
./bootstrap.sh --discover
./bootstrap.sh --blueprint
./bootstrap.sh --bootstrap
```

Selector предлагает All, None или Edit для каждой непустой item-области. Edit
показывает текущее состояние checkbox на страницах по 10 компонентов, а
введённые отдельные номера, списки и диапазоны переключают эти checkbox.
Существующий Blueprint можно изменить повторным запуском `--blueprint`.
Selector сохраняет изменения только после подтверждения; отмена оставляет
существующий файл без изменений и не создаёт новый.

`config/blueprint.conf` остаётся локальным, приватным и исключённым из Git.
Dry-run пока не реализован.

# Конфигурация и модули

Конфигурация содержит **данные**.

Модули содержат **логику работы с этими данными**.

Поэтому пользовательская настройка не должна без необходимости
дублироваться внутри кода.

Например, если Discovery определил размер Dock, Bootstrap должен
получать это значение из конфигурации, а не содержать собственное
фиксированное значение.

Это позволяет изменять настройки рабочего окружения без
редактирования логики Bootstrap.

---

# Форматы

Toolkit не требует единого формата для всех конфигураций.

Формат выбирается в зависимости от типа данных.

Могут использоваться:

* простые конфигурационные файлы;
* структурированные `.conf`;
* JSON;
* специализированные форматы для отдельных подсистем.

При этом формат не должен влиять на общую архитектуру:

```text
Discovery
    ↓
Generated Configuration
    ↓
Blueprint
    ↓
Bootstrap
```

# Dry-run

Dry-run запланирован как безопасный режим работы Bootstrap и пока не реализован.

Он будет использовать существующие проверки и конфигурацию, но не должен
изменять состояние системы.

Основная задача Dry-run — показать, какие изменения Bootstrap
собирается выполнить:

```text
Current State
      ↓
Bootstrap Checks
      ↓
Planned Changes
```

Dry-run должен:

* выполнять проверки состояния;
* определять необходимые изменения;
* показывать предполагаемые действия;
* использовать существующий механизм логирования;
* формировать понятный Summary;
* не применять изменения к системе.

Dry-run не является отдельным источником конфигурации
и не определяет Desired State.

Он будет безопасным способом предварительного выполнения
существующего Bootstrap workflow.

---

# Основные принципы

Конфигурационная система должна обеспечивать:

* разделение данных и логики;
* разделение Observed State и Desired State;
* отсутствие ненужного дублирования;
* воспроизводимость;
* расширяемость;
* совместимость между Discovery и Bootstrap;
* возможность добавления новых компонентов без изменения
  существующей архитектуры;
* возможность будущего безопасного предварительного выполнения через Dry-run.

---

# Архитектурное правило

> **Configuration describes the environment.**
> **Modules define how to work with it.**

Изменение пользовательской настройки по возможности должно
осуществляться через конфигурацию, а не через изменение
Bootstrap-кода.

Generated Configuration описывает фактически обнаруженное
окружение и используется как источник данных для Bootstrap.

Blueprint определяет выбранное целевое состояние для Bootstrap.

Dry-run после реализации позволит безопасно проверить предполагаемые изменения
Bootstrap до их фактического применения.

Текущий реализованный цикл:

```text
Discovery
    ↓
Generated Configuration
    ↓
Blueprint
    ↓
Bootstrap
```

Будущий цикл после реализации Dry-run / Preview и Verification:

```text
Generated Configuration
    ↓
Blueprint
    ↓
Dry-run / Preview
    ↓
Bootstrap
    ↓
Verification
```
