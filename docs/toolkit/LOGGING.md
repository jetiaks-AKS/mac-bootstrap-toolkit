# Logging System

## Назначение

Logging System отвечает за единый и предсказуемый вывод
Mac Bootstrap Toolkit.

Все основные модули используют общий механизм логирования,
чтобы сообщения имели единый формат и поведение.

Logging System также обеспечивает сохранение истории запусков
Toolkit и позволяет анализировать результаты предыдущих операций.

Основные цели:

- единый визуальный стиль;
- понятные сообщения;
- разделение обычного вывода и диагностики;
- минимальный шум в стандартном режиме;
- подробная информация при необходимости;
- сохранение истории запусков;
- корректное завершение логирования при прерывании Toolkit.

---

# Типы сообщений

## Action

Показывает выполняемое действие.

```text
[....] Installing Homebrew packages...
```

Используется для основных операций, выполняемых Toolkit.

Action обычно отображается пользователю в стандартном режиме.

---

## Success

Показывает успешное завершение операции.

```text
[ OK ] Homebrew already installed
```

---

## Warning

Показывает ситуацию, которая требует внимания,
но не обязательно останавливает работу Toolkit.

```text
[WARN] Configuration file not found
```

Warning не используется для обычного информационного вывода.

---

## Error

Показывает ошибку, из-за которой операция не может
быть нормально завершена.

```text
[ERROR] Bootstrap failed
```

Сообщение должно по возможности объяснять причину проблемы.

---

## Info

Используется для дополнительной информации и диагностики.

```text
[INFO] Repository: mac-bootstrap-toolkit
```

`info()` показывает информационное сообщение пользователю и записывает его в
лог. Для диагностических подробностей, которые должны появляться на экране
только с `--verbose`, используется `detail()`. History log при этом сохраняет
диагностическую информацию независимо от того, была ли каждая подробность
показана в стандартном выводе.

---

# Режимы вывода

## Standard Output

Стандартный режим работы Toolkit.

Показывает только информацию, необходимую пользователю:

* основные выполняемые действия;
* успешные результаты;
* предупреждения;
* ошибки;
* итоговый Summary.

Стандартный вывод остаётся компактным пользовательским результатом и не
дублирует весь диагностический lifecycle из history log.

Цель стандартного режима — дать понятный результат без
избыточных технических подробностей.

---

## Verbose Mode

Расширенный режим диагностики.

Дополнительно показывает там, где это полезно:

* диагностические подробности;
* подробности выполнения;
* диагностические данные;
* дополнительный контекст ошибок;
* внутренние этапы работы модулей.

Verbose Mode предназначен для разработки, диагностики
и анализа проблем. Он не меняет семантику выполнения. Интерактивный Blueprint
selector может почти не отличаться визуально при `--verbose`, потому что уже
показывает информацию, необходимую пользователю для выбора.

---

# Лог-файлы

Logging System сохраняет историю каждого запуска Toolkit.

Основные каталоги:

```text
logs/
    latest.log
    history/
```

`logs/latest.log` содержит результат последнего запуска Toolkit.

`logs/history/` содержит отдельные исторические логи предыдущих запусков.

Имена исторических логов соответствуют режиму выполнения:

```text
check-YYYY-MM-DD_HH-MM-SS.log
bootstrap-YYYY-MM-DD_HH-MM-SS.log
discover-YYYY-MM-DD_HH-MM-SS.log
blueprint-YYYY-MM-DD_HH-MM-SS.log
```

Таким образом, история позволяет отдельно анализировать:

* Check;
* Bootstrap;
* Discovery;
* Blueprint.

Логи являются рабочими файлами локального Toolkit
и не должны попадать в Git.

---

# Формат логов

Каждая запись лога содержит timestamp:

```text
2026-08-10 19:16:45 [ OK ] Bootstrap completed successfully
```

Это позволяет восстановить последовательность событий
и определить длительность отдельных запусков.

Logging System сохраняет не только пользовательский вывод,
но и диагностическую информацию, необходимую для анализа
работы Toolkit.

---

# Module Lifecycle

Основные модули фиксируют в логе собственный жизненный цикл.

Для каждого модуля могут записываться записи:

```text
[MODULE] START: Homebrew
[MODULE] Changed: No
[MODULE] RESULT: SUCCESS
```

При изменении состояния:

```text
[MODULE] Changed: Yes
```

Для предупреждений и ошибок фиксируется соответствующий результат:

```text
[MODULE] RESULT: WARNING
[MODULE] RESULT: ERROR
```

Если модуль возвращает неожиданный код завершения,
он должен быть отражён как неизвестный результат:

```text
[MODULE] RESULT: UNKNOWN
```

Module Lifecycle предназначен прежде всего для логов
и диагностики и не должен перегружать стандартный пользовательский вывод.

## Blueprint Lifecycle

Blueprint использует собственный минимальный lifecycle в history log:

```text
[BLUEPRINT] START
[BLUEPRINT] Generated configuration: Ready
[BLUEPRINT] Existing configuration: Valid
[BLUEPRINT] RESULT: SAVED
```

При отмене финальная запись выглядит так:

```text
[BLUEPRINT] RESULT: CANCELLED
```

`Existing configuration: Valid` записывается только после успешной валидации.
При stale или malformed Blueprint сохраняются существующие warning/error
семантики без ложной записи `Valid`.

Выбранные элементы, checkbox-операции, ответы по категориям и содержимое
`config/blueprint.conf` намеренно не копируются в lifecycle log. Источником
состояния выбора остаётся сам Blueprint.

---

# Прерывание Toolkit

Logging System корректно обрабатывает прерывание Toolkit
сигналами `INT` и `TERM`.

При прерывании в лог записывается:

```text
[WARN] Toolkit interrupted
Finished : YYYY-MM-DD HH:MM:SS
Duration : Ns
Status   : Interrupted
```

После этого текущий лог сохраняется как `latest.log`.

Это позволяет отличить:

```text
Successful
Failed
Interrupted
```

завершение Toolkit и сохранить диагностический контекст
даже при преждевременной остановке процесса.

# Общие правила

## Единый формат

Все модули используют общий Logger.

Новые модули не должны создавать собственный формат вывода.

## Понятные сообщения

Сообщение должно по возможности объяснять:

* что происходит;
* что произошло;
* что требуется от пользователя, если это необходимо.

## Отсутствие дублирования

Одна операция не должна многократно сообщать
об одном и том же результате.

## Правильный уровень сообщения

Каждое сообщение должно использовать соответствующий тип:

* Action — выполняемое действие;
* Success — успешный результат;
* Warning — ситуация, требующая внимания;
* Error — ошибка;
* Info — дополнительная информация или диагностика.

## Quiet by Default

Обычный запуск должен оставаться компактным.

Технические подробности должны появляться в основном
в Verbose Mode, но при этом сохраняться в логах.

## История запусков

Каждый запуск Toolkit должен создавать собственный
исторический лог.

Последний запуск дополнительно доступен через:

```text
logs/latest.log
```

# Summary

Summary зависит от режима и контекста запуска.

Check, Discovery и Bootstrap без Blueprint используют legacy Summary жизненного
цикла, которое может включать:

```text
Modules Checked
Installed
Skipped
Warnings
Errors
Duration
```

Bootstrap с Blueprint использует Blueprint-aware Summary выбранного scope.
Например, конкретные числа зависят от локальной конфигурации:

```text
Applications
  Homebrew packages      28 / 28 selected
  Homebrew casks          3 / 16 selected

Workspace
  Folders                 2 / 4 selected

Settings
  Git Configuration      Enabled
  VS Code Settings       Skipped

Result
  Warnings               0
  Errors                 0

Duration                 15s
```

`Enabled` в этом Summary означает, что категория выбрана Blueprint, а не что
настройка обязательно была изменена в текущем запуске.

Интерактивный Blueprint selector отдельно показывает selection Summary перед
подтверждением сохранения: selected / total для item-категорий и Yes / No для
категорий настроек. Это не Summary выполнения Bootstrap.

Во всех вариантах детальный lifecycle остаётся в логах и не должен перегружать
пользовательский Summary.

Будущий Dry-run / Preview должен следовать тем же принципам логирования, но его
конкретный Summary ещё не спроектирован.

---

# Архитектурное правило

> **Logging describes what the Toolkit is doing and what happened.**
> **It does not contain business logic.**

Logger отвечает только за представление и сохранение информации.

Решения о состоянии системы, конфигурации и необходимых действиях
принимаются соответствующими модулями.

Logging System должна оставаться независимой от конкретной бизнес-логики.

Реализованные режимы:

```text
Check
Discovery
Blueprint
Bootstrap
```

Dry-run / Preview запланирован, но не реализован. В будущем он должен следовать
тем же принципам разделения компактного вывода и диагностической истории.
