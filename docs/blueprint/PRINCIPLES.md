# Принципы Mac Blueprint

> Основные принципы разработки проекта.

Все архитектурные и технические решения должны соответствовать данным принципам.

Если новое решение нарушает один из принципов, архитектура должна быть пересмотрена.

---

# 1. Пользователь всегда принимает окончательное решение

Toolkit никогда не принимает решения за пользователя.

Он анализирует систему, предоставляет информацию и предлагает выбрать необходимые компоненты.

Окончательное решение всегда остаётся за человеком.

---

# 2. Discovery никогда ничего не изменяет

Discovery — исключительно аналитический модуль.

Он не изменяет систему.

Не устанавливает программы.

Не удаляет файлы.

Не изменяет настройки.

Единственная задача Discovery — показать пользователю полную картину системы.

---

# 3. Никакой "магии"

Toolkit никогда не должен выполнять скрытые действия.

Любое изменение должно быть понятным пользователю.

Перед выполнением любой операции пользователь должен понимать:

- что будет сделано;
- какие компоненты будут изменены;
- почему выполняется данное действие.

---

# 4. Конфигурация отделяется от пользовательских данных

Описание системы и пользовательские файлы являются разными сущностями.

Blueprint хранит описание рабочего окружения.

Пользовательские каталоги сохраняются отдельно.

---

# 5. Blueprint не является резервной копией

Mac Blueprint не заменяет:

- Time Machine;
- Migration Assistant;
- другие системы резервного копирования.

Blueprint описывает рабочее окружение пользователя, а не весь компьютер.

---

# 6. Модульность

Каждый компонент проекта отвечает только за свою задачу.

Например:

- Discovery анализирует систему;
- Blueprint описывает систему;
- Restore восстанавливает систему;
- Compare сравнивает системы.

Модули должны быть максимально независимыми.

---

# 7. Идемпотентность

Любую операцию можно выполнить повторно.

Повторный запуск не должен приводить к ошибкам или дублированию данных.

---

# 8. Self-Healing

При обнаружении проблемы Toolkit должен стремиться безопасно её исправить.

Однако исправление никогда не должно происходить без явного понимания пользователем выполняемых действий.

---

# 9. Прозрачность

Все действия Toolkit должны быть понятными.

Пользователь всегда должен видеть:

- что обнаружено;
- что будет сохранено;
- что будет восстановлено.

---

# 10. Человекочитаемость

Все основные файлы проекта должны быть максимально понятными.

Конфигурации должны легко читаться человеком.

Документация должна объяснять архитектуру, а не только команды.

---

# 11. Простота важнее сложности

Если задачу можно решить простым способом без потери функциональности,
следует выбирать простое решение.

Не использовать сложные алгоритмы там, где достаточно понятного списка и выбора пользователя.

---

# 12. Архитектура важнее реализации

Сначала проектируется архитектура.

Только после её утверждения начинается реализация.

Код является следствием архитектуры, а не наоборот.

---

# Главная философия проекта

Toolkit не пытается быть умнее пользователя.

Он помогает пользователю понять собственное рабочее окружение, самостоятельно собрать Blueprint и затем воспроизвести его на любом новом Mac.
