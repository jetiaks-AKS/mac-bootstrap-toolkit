# State Convergence

> **Статус: Concept / Long-term direction**

Этот документ исследует возможное долгосрочное развитие Mac Bootstrap Toolkit.
Он не является контрактом реализации, Roadmap или спецификацией следующего
этапа разработки. Текущая реализованная архитектура определена в
[ARCHITECTURE.md](../toolkit/ARCHITECTURE.md), запланированное развитие — в
[ROADMAP.md](../../ROADMAP.md), а ближайшая техническая работа — в
[TODO.md](../../TODO.md).

## Назначение

Toolkit может развиваться от воспроизведения выбранных частей Mac к осознанному
приведению результата к выбранному пользователем целевому состоянию:

```text
Discover → Describe → Select → Plan → Apply → Verify
```

Это направление полезно тем, что разделяет обнаружение, намерение пользователя,
план действий, применение и подтверждение результата.

## Границы статуса

Реализовано в `develop`:

- Discovery и Generated Configuration;
- Blueprint MVP с выбором категорий и отдельных элементов;
- фильтрация Bootstrap через Blueprint;
- legacy all-inclusive Bootstrap при отсутствии Blueprint;
- Bootstrap как текущий механизм применения.

Запланировано в Roadmap, но не реализовано:

- Dry-run / Preview;
- Verification.

Долгосрочные концепции, не являющиеся обязательствами по реализации:

- несколько именованных Blueprints / Profiles;
- более развитое планирование восстановления и полезная переносимость;
- возможные import / export;
- возможный отдельный Restore Engine.

## Концептуальная модель

```text
                    Current Mac
                        │
                        ▼
                    Discovery                 [реализовано]
                        │
                        ▼
                  Observed State
                        │
                        ▼
             Generated Configuration          [реализовано]
                        │
                        ▼
                    Blueprint                 [MVP реализован]
                  /      |      \
          Default*     Dev*    Server*         [концептуальные profiles]
                  \      |      /
                        ▼
                  Desired State
                        │
                        ▼
                  Plan / Preview               [запланировано]
                        │
                        ▼
                       Apply                   [сейчас Bootstrap]
                        │
                        ▼
                  Verification                 [запланировано]
                        │
                        ▼
                 Converged State

* Только примеры; несколько именованных Blueprints не реализованы.
```

## Observed и Desired State

Generated Configuration содержит обнаруженные machine-specific значения.
Blueprint выражает целевой выбор без ненужного копирования этих значений:

```text
Observed State
    ↓
Generated Configuration
    ↓
Blueprint selection
    ↓
Desired State
```

Разделение обнаружения и выбора не позволяет Blueprint превратиться во второе
хранилище конфигурации и сохраняет однозначный источник обнаруженных данных.

## Именованные Blueprints / Profiles

Полезная долгосрочная интерпретация:

```text
Profile ≈ named Blueprint
```

Blueprint отвечает на вопрос: «Что из обнаруженного состояния должно войти в
целевое состояние?». Именованный Blueprint, или Profile, дополнительно отвечает:
«Для какой роли машины или сценария использования?». Примерами могут быть
Default, Development, Personal, Server или Full.

Один из возможных вариантов структуры:

```text
config/
└── blueprints/
    ├── default.conf
    ├── development.conf
    ├── personal.conf
    └── server.conf
```

Это только пример, он не реализован. Profiles должны переиспользовать семантику
Blueprint, а не требовать отдельного Profile Engine, и не запланированы на
следующий релиз.

## Plan / Preview

Dry-run / Preview со временем может стать полезнее, чем простой запуск
Bootstrap без изменений. На основе Blueprint мог бы формироваться понятный
человеку план целевых изменений, который затем выполняет Apply:

```text
Blueprint → Restore Plan / Preview → Apply
```

План мог бы описывать результаты Install, Configure, Create, Already satisfied,
Skip, Warning и Error. Точные форматы и API намеренно не определяются. Preview
остаётся нереализованным, а его фактический дизайн относится к будущему этапу
Roadmap.

Важный долгосрочный принцип: Preview и Apply должны описывать и выполнять один
и тот же план целевых изменений, а не независимо вычислять разное поведение.

Вычисление плана по возможности должно оставаться отделённым от его отображения
в терминале:

```text
Desired State
    ↓
Plan logic
    ↓
Structured result
    ├── CLI rendering
    └── future GUI rendering
```

Сейчас это не требует публичного API, JSON-формата, framework, GUI backend или
planner abstraction. Принцип лишь сохраняет возможность показывать один и тот
же план через разные интерфейсы без дублирования planning logic.

## Apply и Bootstrap

Bootstrap остаётся текущим механизмом применения. В будущем он может начать
координировать связанные фазы:

```text
Bootstrap / Apply
    ├── Plan
    ├── Apply
    └── Verify
```

Это концепция, а не текущая архитектура. Apply должен оставаться идемпотентным,
проверять состояние до изменений, защищать пользовательские данные и
подтверждать применённые изменения там, где это поддерживается.

## Verification

Verification должен со временем отвечать на вопрос: «Достиг ли получившийся Mac
выбранного целевого состояния?»

```text
Observed / resulting state
            ↕
       Desired state
```

Это отличается от проверок перед применением и от одного лишь успеха команды.
Verification запланирован, но пока не реализован; конкретный framework здесь не
определяется.

## Интерфейсы

Одинаковое поведение Toolkit со временем может быть доступно через разные
интерфейсы:

```text
Toolkit Core
    ├── CLI
    ├── Unified interactive workflow
    └── Future GUI
```

CLI остаётся first-class интерфейсом для расширенного использования,
автоматизации, разработки и диагностики. Будущий GUI должен быть слоем
представления над той же логикой Toolkit, а не отдельной реализацией Discovery,
Blueprint, Apply или других операций. GUI остаётся концепцией и не запланирован
для конкретного релиза.

## Unified workflow

Wizard или GUI со временем может объединить отдельные операции в единый
пользовательский flow:

```text
Discover → Select → Preview → Confirm → Apply → Verify
```

Сегодняшние отдельные CLI-режимы остаются полезными и не должны исчезать.
Unified workflow является концепцией и не определяет команды, flags, screens
или GUI technology.

## Optional Restore Engine

Исходная концепция предполагала отдельный Restore Engine. После реализации
Blueprint возможен более простой путь: Bootstrap может естественно развиться в
слой оркестрации Plan → Apply → Verify.

Отдельный `modules/restore/` не является обязательным или неизбежным. Его
необходимость следует оценивать только после появления реальных реализаций
Preview и Verification и только если их оркестрацию нельзя будет чисто сохранить
внутри Bootstrap.

## Принципы дизайна

1. Observed state и desired state остаются разделены.
2. Выбор не дублирует machine-specific данные без необходимости.
3. Каждый новый слой строится на работающих нижних слоях.
4. Preview и Apply со временем должны использовать один и тот же план.
5. Вычисление Plan остаётся отделимым от его представления в CLI или будущих        интерфейсах.
5. Apply остаётся идемпотентным и безопасным.
6. Verification оценивает итоговое состояние, а не только успех команды.
7. Profiles переиспользуют семантику Blueprint вместо создания нового Engine.
8. Отдельный Restore Engine появляется только при оправдывающей его сложности.
9.  Обратная совместимость сохраняется там, где это практично.
10. Optional-возможности не усложняют MVP-архитектуру преждевременно.

## Связь с исходной концепцией

[MAC-BLUEPRINT.md](MAC-BLUEPRINT.md) хранит исходную историческую идею. State
Convergence модернизирует это направление с учётом опыта реализации Discovery,
Generated Configuration, Bootstrap и Blueprint. Документ сохраняет стремление
к осознанному приведению Mac к целевому состоянию, не превращая
speculative-возможности в текущие обязательства.
